Your fork, upstream’s releases, and an agent in between

Agents make it easy to change the software you run. GitSpace makes the agent keep your changed copy current: every upstream release arrives as a merge into your branch, done in a workspace, reviewed like any pull request, launched when you say so.

feels like there needs to be a new way to distribute opensource software such that people can modify via agents but also get upstream automatically merged in

coding agents can do this but they won’t do it automatically

Thariq (@trq212), Oct 27, 2026

This is a problem we had to solve for ourselves, because GitSpace is distributed exactly this way. Every account runs its own copy of GitSpace, and the source of that copy is a project inside the account, open to the same agents you use for everything else. If you want GitSpace to behave differently, you ask an agent to change it. And then you still want next week’s release.

Every account runs its own GitSpace

A GitSpace account isn’t a tenant in a shared app. It runs its own Worker, its own frontend and its own machine runtime, and it chooses which release each of those runs. Every account also has a GitSpace project: the repository its GitSpace is built from, with a base branch, workspaces and a project agent like any other project.

Out of the box that project points at upstream, inKibra/gitspace.sh on develop. Point it at your fork instead, and your fork is what the account builds. Customizing GitSpace is then just working in that project: an agent changes the code in a workspace, you try the result as a trial on the frontend, the Worker or your machines, and either keep it or go Back to default. A trial never changes the account’s default release; promoting one means merging it into the branch the project builds.

The part agents don’t do on their own

Thariq’s point is the second half. An agent will happily merge upstream into your fork if you ask. Nobody asks. Releases go by, the fork drifts, and the merge that would have taken ten minutes in October takes an afternoon in March.

So we don’t rely on anyone asking. The asking is an automation, and the merging is a workspace.

The loop

  1. A release is published upstream. Every GitSpace project starts with one automation, GitSpace releases: watch the releases of the project’s repository, or of its upstream parent when the project builds a fork, for tags matching v*. It hears about a release through the account’s GitHub App the moment it’s published, or by checking once a day.
  2. The project agent reads it against what you run. The automation hands the release to the project agent, which reads the release notes, what the account runs and what your branch changes, and says in a few lines what the release would change for you.
  3. It asks. One question, with the answers spelled out.
  4. A workspace does the merge. The agent starts a workspace on its own branch, merges the tag into your branch there and resolves the conflicts. It isn’t resolving them blind: it has your branch’s history, and the goals and journal entries your agents recorded when they made those changes. It runs the checks, then opens a pull request into your branch.
  5. Review happens where it always does. The pull request is linked to the workspace. Default automations send failed checks back to it (“Checks failed on this workspace’s branch. Find out why and fix it.”) and send your review comments to it, so you review a merge the way you’d review any change, and the agent keeps working on it until you’re happy.
  6. You merge; it asks to launch. Once the pull request is merged, the project agent asks whether to build your branch and launch it. A build runs on one of your machines and takes a few minutes; you can launch it as a trial first. If anything is wrong, Back to default puts the previous release back.

Your agents keep working through it

A release you launch shouldn’t cost you the work your agents are in the middle of. Usually, upgrading the system an agent runs on means stopping it: the session dies, the context is gone, and you start over and re-explain. GitSpace is built so that upgrades aren’t an event your agents notice.

Every workspace’s agent runs on pi-durable, which makes the durable record the state: its conversation, its subagents, its queued messages, its running tasks and its documents are committed before they’re shown, in the workspace’s own Durable Object. Nothing important lives only in memory. So when a release goes out:

  • Agents finish what they’re doing first. The release tells every workspace to move to the new code between turns. An idle one moves at once; a busy one waits until its current work ends.
  • An interruption is resumed, not lost. If a workspace is restarted mid-turn anyway, pi-durable resumes its tasks from their last checkpoint, losing at most a fraction of a second of model output. A tool call that was running on a machine comes back to the agent as interrupted, with its output so far, and the agent carries on from there.
  • Your machines keep their processes. When a machine updates, the dev servers and terminals your agents started keep running under the new version.
  • Conversations stay where they were. A queued message, a subagent working in the background, a question waiting for your answer: all of it is still there after the release, on the new code.

That’s what makes it reasonable to say yes to the release question in the middle of a working day. The merge workspace, the release, and the agent working on your actual project all keep going.

Why it’s safe to leave on

ConcernWhat GitSpace does
An agent acting on its ownThe automation asks before merging or launching. You can edit it to act without asking; an automation an agent proposes does nothing until a person turns it on.
What “a release” isReleases are pinned: a commit plus the SHA-256 of its manifest, which lists the SHA-256 of every file. A pin fixes every byte of one release.
A bad merge reaching productionThe merge lands as a pull request on your branch, with your checks. Launching is a separate answer, can be a trial, and Back to default undoes it.
Agents talking themselves into loopsEach run has provenance; a release a run produced doesn’t start a new run; rounds per subject and runs per day are capped.
Untrusted inputWatching another repository is an explicit trust decision a person makes. Events from people without write access to your repository don’t reach an agent.

What’s still hard

Merges aren’t the hard part; meaning is. A conflict where upstream renamed a function you also changed is easy for an agent. A release that changes the behavior your customization depended on, with no textual conflict at all, is not, and that’s exactly the case where the merge goes through cleanly and still breaks you. The pull request and your checks are the defense, and the agent’s summary of “what this release changes for you” is the early warning. We think the right default is an agent that does the work and a person who says yes.
