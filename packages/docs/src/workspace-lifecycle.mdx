# Workspace lifecycle

Use the normal workspace agent to configure repository setup. The built-in `workspace-lifecycle` skill inspects your repository, proposes changes, and separates permission to edit from permission to execute.

Selecting a project or workspace does not run setup. Creating a workspace does not provision cloud resources.

## Cloud workspaces and base branches

Workspace creation, ordinary Git source resolution, archive, and restore run in the cloud without an attached machine. A new workspace uses its saved phase, including after its runtime reopens. Human phase changes and approved plans update that saved phase; a workspace still cannot advance beyond its dependencies.

Sources can name the project base branch, an imported branch or commit, another workspace's committed HEAD, a tag, or a pull-request head. Missing public tag and pull-request refs are fetched from the canonical HTTPS origin into the project's Artifacts repository before the workspace forks it. Annotated tags are resolved to their commits. This fetch sends no account credentials to the origin and does not follow redirects: use the final repository-root URL. Ref advertisements are limited to 64 KiB, Git packs to 40 MiB, and each fetch to 15 seconds. Private or oversized initial imports still require the existing machine-seeding flow.

Changing a project's base branch switches its existing base workspace checkout as well as its saved branch and source commit. Other workspaces retain their branches. The base checkout must be clean, its agent stopped, and its machine caches detached. Staged, unstaged, conflicted, or held-back LFS changes are rejected before branch mutation; they are not discarded. If a ref publication is interrupted, the base runtime remains fenced: repeat the same base-branch change to complete recovery before using it.

Legacy machine-held workspaces cannot silently become cloud runtimes. They must be migrated from their original machine checkout before cloud lifecycle operations are available.

## Configure a repository

1. Open the cloud workspace for repository inspection and edits, and configure its inference profile. Attach a machine in Environment when you are ready to execute checks or lifecycle scripts; conversation and ordinary cloud Git work do not require that machine.
2. Ask: **Use the workspace-lifecycle skill to inspect this repository and propose its lifecycle configuration. Do not edit or execute yet.**
3. Review the proposal. It should name the files to change, required tools, profiles, secret names, existing resource IDs, costs, and any cloud effects.
4. Approve the repository edits. The agent can now write the agreed configuration and check its syntax. This does not authorize installs, repository checks, provisioning, or teardown.
5. Review the final diff and the Environment panel. Choose the profile and provide non-secret values. Put credentials in the project's secret store, not the repository or lifecycle bindings.
6. Approve the exact check and script content in Environment. Give separate authorization to execute setup, then use the Environment setup action or ask the agent to use the shared environment API.
7. Inspect the recorded run and its logs. If it fails, keep the workspace open and repair the failing step. Do not assume failure means no resource was created.

The skill ships through the existing Skills system and defaults to project and workspace agents. Account skill settings can disable it or change its assignment. There is no separate setup agent.

Content approval allows repository code to run as the machine user, using that user's home configuration and available credentials. GitSpace keeps the user's tool search path and prepends its managed tools directory. This is not a sandbox: secret grants control injected secrets, not every credential on the machine. Review helper scripts and package install hooks as well as lifecycle entry scripts. Neither content hashes nor log redaction protect against all behavior of code you authorize.

## Split work by what survives

| Phase | Put this work here | Do not put this work here |
| --- | --- | --- |
| `cloud/provision` | Create or adopt resources owned by the durable workspace | Dependency installation in the current checkout |
| `machine/prepare` | Prepare tools needed on this machine | Workspace-specific generated files |
| `workspace/materialize` | Install checkout dependencies and rebuild local configuration | Creating a second cloud stack on each arrival |
| `workspace/dematerialize` | Flush local state and release local leases before leaving | Deleting remote databases, buckets, or deployments |
| `cloud/destroy` | Delete recorded workspace-owned resources after explicit retirement authorization | Cleanup on selection, close, or move |

Keep long-running services in `.gitspace/services.json` and run them through GitSpace service controls. Lifecycle scripts should finish, not leave unmanaged background processes.

Explicit setup enables the workspace's automatic local-preparation policy. It runs machine preparation, checks, provisioning, and materialization in order, stopping on failure. Later arrivals can run approved local preparation only after provisioning has succeeded. Changed or unapproved content waits for approval. A successful cloud provision belongs to the workspace identity, not a checkout. Moving or editing a script does not automatically provision it again.

A direct `workspace/materialize` request runs local reconstruction only; it never creates or adopts cloud resources first. If a materialization script requires recorded ownership bindings, establish them through approved `cloud/provision` or adoption before materializing. Do not bypass ownership checks or copy another workspace's bindings to make setup pass.

## Machine copies and the Environment panel

The workspace header has one **Environment** chip. It opens **Inspector > Environment**, with the current profile and default machine, followed by each machine's setup, activity, sync state, and logs. Waiting approvals appear beside the blocked machine. The same panel retains the editable lifecycle definition, secrets and values, browser-origin approvals, and recent runs.

Normal attachments are equal caches of the cloud working tree. Each machine uses its standard workspace path and runs machine preparation, checks, and materialization under the same approval rules. A successful setup on one machine does not prove that another machine is ready. **Setup again** records a new run; **Make default** changes routing without moving the workspace.

Before **Run checks** or a lifecycle phase, choose **Run on machine**. The panel may preselect the workspace's explicit default cache or its only ready cache; with multiple ready caches and no default, you must choose. Every request names that machine. A missing or stale attachment is an error, never a fallback to another online machine. Paused caches resume through the normal cache setup lifecycle before the run. With no attached machine, records and configuration remain available but execution is disabled.

Terminals open on a machine you choose. The terminal pane lists the machines attached to the workspace as ready caches; pick one, and its shells start in that machine's copy with the bundle's [terminal environment](/lifecycle-reference#terminal-environment). There is no default terminal machine: the default machine only routes commands. With no ready cache, the pane offers **Attach a machine**, which opens Environment. Every terminal request names its machine, and the account refuses one that is not a ready cache of the workspace.

Commands catch up before execution and publish changes when they finish. Services and running processes publish periodically. Continuous sync ends after active work stops and a 15-minute grace period expires. Attaching a terminal or enabling **Work locally** also starts a human file watcher. Viewing the workspace in a browser does not start that watcher.

An idle copy pauses before it is reclaimed. The default reclaim delay is 24 hours; the workspace cache policy can change it. Low disk space may trigger earlier reclaim of an idle copy. A final acknowledged snapshot, no held-back LFS edits, and no unresolved effects are required before deletion. **Reclaim now** uses the same barriers. The next command rebuilds the copy and runs approved local setup again. Machines without a heartbeat for 30 seconds cannot receive new work; reconnecting requires catch-up before they become ready.

## Release caches, archive, and retire

Opening a project or workspace opens its cloud view; it does not claim a machine or restore a holder. Use **Environment > Add machine** when you need a machine cache for commands or terminals.

**Release machine caches** asks each attached normal cache to drain and detach. It does not archive the workspace, stop its cloud conversations, or detach private runner and delegate checkouts. The cloud workspace stays available, and Environment can attach a cache again. No attached cache is reported explicitly rather than treated as a closed workspace.

**Archive** stops the workspace's agents, asks its machine attachments to drain, and marks its saved definition archived. **Restore** reactivates that definition in the cloud without requiring an online machine. Retirement is a separate, explicit decision about cloud resources; releasing caches and archiving never authorize remote destruction.

If the original machine is gone, attach another authorized online machine to this workspace, then select it in Environment for explicit retirement. Cache setup restores the canonical working copy and honors preparation approvals before the requested destruction runs. Choosing a machine does not authorize scripts or retirement. Failed destruction preserves the cloud records for recovery.

Before a cache is deleted, its machine drains activity and completes the publication and execution-reconciliation barriers. Held-back LFS changes require a commit or explicit confirmation before release. A failed drain or publication keeps local files available for recovery; requesting release is not proof that the machine has finished detaching.

Private runner and delegate checkouts have a separate drain step. GitSpace verifies the attachment generation, stops owned processes, confirms that any mount is gone, and refuses deletion while execution claims remain unresolved. A lost attachment fences work but does not authorize deleting files. Normal cache reclamation has its own final-snapshot and held-back-change barriers.

Pi conversation state lives in the cloud, not in the checkout. The checkpoint records its cloud session and conversation reference alongside the saved code and artifact state. Moving a checkout does not transfer ownership of the conversation to the destination machine.

A fresh arrival recreates local state. Do not rely on files left behind on the previous machine, even when you return to it.

| State | What to expect after cache reclamation |
| --- | --- |
| Git commits and branch; staged and unstaged tracked changes | Saved by a completed checkpoint |
| Non-ignored untracked files | Saved by a completed checkpoint |
| Pi agent conversation | Kept in cloud runtime storage; the checkpoint records its reference |
| GitSpace `local://` evidence artifacts | Saved separately from the code repository, with encrypted artifact storage |
| Profile, values, approvals, script snapshots, bindings, provision identity, run records and logs | Kept in the cloud lifecycle ledger, outside the checkout |
| Ignored `.env`, `node_modules`, caches, build output | Not checkpointed; recreate during materialization |
| Machine packages and arbitrary home-directory files | Not workspace state; prepare again where needed |
| Remote resources | Remain until you explicitly authorize their destruction |

<Warning>
A checkpoint is not a disk backup. If you keep a database only in an ignored local file, releasing or reclaiming its machine cache can lose it. Use durable remote storage or an explicit export that the checkpoint captures. Never export secrets into tracked or non-ignored files.
</Warning>

After an unexpected interruption, the last completed checkpoint remains the recovery limit for local work. An interrupted cloud command may have taken effect without reporting success. Inspect the provider and recorded bindings before authorizing recovery. GitSpace must not retry an uncertain cloud effect in the background.

Cloud conversation recovery does not restart an unresolved shell command or lifecycle script. The machine supervisor reconciles recorded process identity and execution evidence. A disconnected machine may still be running the original effect.

## Interactive authentication

Prefer setup that runs unattended. When a provider requires human authentication, choose **Run interactively** for the approved phase in Environment. A dedicated **Environment** terminal appears for the script's prompts. The confirmation explains that a person must remain available and that terminal output will not be saved.

Scripts can declare this requirement with `# gitspace: interactive` in their leading comment header. Automatic preparation stops before launching a phase that requires interaction. Review and approve changed script content before starting it. See the [interactive script reference](/lifecycle-reference#interactive-scripts).

The terminal lists scripts in execution order, with each step's status and exit code. Fast steps remain visible as completed. When the run succeeds or fails, input stops but the visible output stays in the open pane so you can read the final error.

The runner still owns the deadline, cancellation, and result. Closing the pane or reloading discards its private output but does not stop a running script. Reopening reconnects to that same process without replay. A broken connection also clears private output. The terminal never leaves a shell with the script's injected secrets.

Input echo is disabled, and raw terminal input and output stay out of persistent logs and replay. Recorded results contain safe execution metadata, not the authentication conversation. Approved scripts may write credentials into protected, ignored local files. Those files are not checkpointed: expect to authenticate again after a move or session expiry. This feature does not share sessions across projects or machines.

This machine-local authentication is for lifecycle scripts and their tools. Inference-provider login and refresh use the cloud credential vault instead; they do not depend on an Environment terminal or a connected machine.

## Recover a failed setup

Open Environment and read the phase's recorded result and logs. For interactive runs, read private error output in the still-open terminal; saved history contains only safe execution metadata. Preparation failure does not gate the workspace page. Use the agent or terminal when its own prerequisites are available.

**View log** opens one script's output and exit status at a time. Scroll down to load more, or use **Copy selected script** to load and copy that script's complete recorded output. Running scripts copy output recorded so far. A later script failure does not change an earlier script's successful result; a script without a recorded exit is not reported as a confirmed failure. Older unframed logs may offer only a clearly labeled saved preview, not a complete-copy action.

For local failures, fix the configuration, review changed content, approve it, and run the needed phase. For cloud failures, first inspect the bindings and provider state. Scripts should record each resource ID as soon as the provider returns it, including when a later step fails.

A failed explicit provision rerun does not erase the previous successful provision. Do not rerun just to make a status label green. Decide what the provider needs, then authorize that specific recovery.

## Migrate old hooks

Old `pre`, `setup`, `select`, and `remove` hooks need an explicit migration. They are not aliases for the new phases and must not silently execute.

Ask the skill to inventory each command and propose a split:

- Move cloud creation out of `setup` into `cloud/provision`.
- Move machine tools into `machine/prepare`.
- Move checkout-local work from `pre`, `setup`, or `select` into ordered `workspace/materialize` scripts.
- Move only local flush or lease-release work into `workspace/dematerialize`.
- Move remote deletion from `remove` into `cloud/destroy`. Never map it to dematerialization: that would delete resources on every move.

Approve the edits, remove the obsolete hooks, and inspect the new script hashes. Adopt existing remote resource IDs before execution. A missing local cache is not evidence that a resource needs to be created again.

See the [lifecycle reference](/lifecycle-reference) for filenames, profiles, script inputs and outputs, and complete local-only and cloud-adoption examples.
