# Core concepts

## Account

A GitSpace account owns its devices, machines, projects, workspaces, settings, and product state. Each account has a permanent handle and its own account Worker, relay endpoint, state, and storage.

The account root key is the authority that enrolls machines and browsers. The `gsr_` recovery key is an encoding of that private root key.

The sidebar belongs to the account, not to an agent session. Projects and Account settings remain available when no agent or machine is running. Closing the last open project or workspace leaves the app open, with access to saved cloud records.

## Browser device

A browser enrolls from a one-time invitation created by an authorized browser, or with your recovery key. It generates a non-extractable Ed25519 key in IndexedDB and signs RPC requests with that key. `gitspace open` opens the account URL; it does not create an invitation.

Browser grants are revocable. Enrolling a new browser does not require sharing another browser's private key.

## Machine

A machine is a physical computer or managed sandbox that materializes checkouts and runs authorized effects. A physical machine runs the runtime started by `gitspace machine start`. Pi sessions and inference run in the cloud, not in a machine child process.

Machines expose capabilities such as available runtimes, isolation, hardware, services, and credential scopes. Placement uses those capabilities to keep work on an eligible machine. GitSpace also reports machine state such as online, offline, starting, stopping, or error so the fleet view can direct attention.

Cloud machines are temporary. **Stop** saves supported workspace state before stopping; if saving fails, the machine stays online. **Start** runs a fresh machine environment and restores saved workspaces. Neither a new machine nor Start restores the old machine disk. Installed packages, machine-local configuration, ignored files, and other files outside GitSpace's checkpoints do not survive Stop or replacement. This includes arbitrary files in the machine's home directory.

Ask a normal workspace agent to use the built-in `workspace-lifecycle` skill to plan repeatable tool preparation. Approve configuration edits first, then approve execution separately. Machine changes remain temporary; there is no separate setup agent. See [Workspace lifecycle](/workspace-lifecycle).

## Project

A project groups work for one repository. It is the stable parent for that repository's workspaces.

## Workspace

A workspace is an isolated, durable unit of change. Its cloud Durable Object owns Pi conversations, task state, questions, and workspace documents. Opening it on a machine materializes a checkout; closing that checkout does not transfer conversation authority to or from the machine.

A completed checkout checkpoint saves supported Git state: the branch, commits, staged and unstaged tracked changes, and non-ignored untracked files. Cloudflare Artifacts stores code repositories. GitSpace's encrypted evidence manifests and blobs are a separate store, not repository branches or ArtifactFS mounts.

A checkpoint is not a backup of the whole machine. After unexpected disk loss, the last completed checkpoint limits checkout recovery; uncheckpointed files may be lost. Durable conversation state does not restore those files or prove that an interrupted machine effect finished. Automatic recovery from unclean disk loss and a returning-machine recovery ZIP are not implemented yet.

Workspace phases are:

| Phase | Purpose |
| --- | --- |
| `plan` | Define intent, requirements, and approach. |
| `code` | Implement and verify the change. |
| `review` | Read the diff, evidence, review threads, and change guide. |
| `ship` | Release the work and watch its operational state. |

A workspace can attach to eligible machines, with explicit placement for its checkouts and tasks. Each machine keeps an equal cache of the canonical cloud working tree, with one fenced writer for each admitted mutation. Runners use a recorded source commit rather than sharing a mutable filesystem. Losing a connection does not prove that an old command stopped, so unresolved effects must reconcile before they can safely repeat. A GitSpace workspace can also modify and release the account's own GitSpace code, subject to approval.

## Account releases

The account selects three active release targets independently: Worker, frontend, and machine. Updating one target keeps the others on their selected releases. Pi ships with the cloud runtime. Historical OMP selections remain release history; they do not launch OMP or provide a machine-session fallback.

Machine updates drain and replace the machine process. An older native-v1 host needs the existing authenticated recovery/bootstrap path before it can accept native-v2. Selecting the new release does not make that predecessor capable of activating it.

Runtime releases carry an authenticated file inventory and compatibility requirements for the operating system, architecture, Bun version, and machine protocol. Activation checks the complete payload against its content hashes, including native modules. Replacement plans retain rollback state until all targets commit.

The account selects cloud images independently for each machine, plus a default for new machines. The platform supplies provider infrastructure; changing one machine's selected image does not update the others. An image supplies the operating system, tools, and initial runtime, so replacing it is separate from updating account code inside the running VM. Image replacement checkpoints the source, confirms it has stopped, and keeps admission closed until the replacement restores the previously open workspaces. Stopping a Cloudflare VM discards its ephemeral disk; status and checkpoint-control requests must not silently start a fresh VM.

## Agent session

A Pi session belongs to a workspace's cloud runtime. The browser renders its conversations, tool results, questions, and task state. Inference and credential refresh can continue without an online machine; operations that need a checkout or process still need an authorized executor.

The live runtime view is bounded. It projects the newest 256 entries per conversation, active tasks, and the newest 128 terminal task records. Older durable entries and receipts remain stored; the live view is not a complete history export. Slow or stale subscribers reconnect for a fresh snapshot rather than growing an unbounded event queue.

Cloud recovery restores durable session state and reconciles pending work. It does not blindly replay an uncertain machine effect, turn a stored job into a live process, or answer a pending human question. Protected lifecycle terminal input and output remain outside agent-readable transcripts and general process logs.

Saved OMP conversations remain historical records. GitSpace reads supported JSONL transcript formats through version 3 without launching OMP; newer unsupported formats report an error. Those archives do not become live Pi sessions, and a saved checkpoint cannot recreate an old process. Archive views and their history controls are separate from the bounded Pi runtime view.

### Agent definitions

Keep repository agent files in `.agents/agents/*.md`. GitSpace also reads
`.omp/agents/*.md` from existing projects. An agent's frontmatter `name`
identifies it; without one, GitSpace uses the filename. When both directories
define the same name, `.agents/agents` wins regardless of discovery order.
**Inspector > Agent setup** shows the winning and ignored paths.

Agent setup reads committed repository definitions without an attached machine.
Saving there keeps a revision-checked cloud override for that path, not a
working-tree edit. Directory precedence still applies. The change affects
future agent starts; existing subagents keep their retained definitions.

## Inspector products

Each workspace can expose the following durable products:

- **Goal** for intent and observable requirements.
- **Workflow** for the current execution contract.
- **Rubric** for how the result will be judged.
- **Journal** for phase narrative, decisions, and state snapshots.
- **Review** for evidence-backed threads on the change.
- **Change Guide** for a reviewable explanation of the final diff.
- **Artifacts** for files and proof produced by the work.
- **Services** for running processes and previews.

These products stay attached to the workspace instead of disappearing when an agent session ends.

Opening Inspector does not open a checkout or start a machine. It can read cloud records such as goals, workflow, rubric, journal, review, Change Guide, and referenced artifacts while machines are offline. Cloud conversations and committed repository reads do not depend on a live checkout.

Working-copy files, staged or uncommitted changes, terminals, processes, and services require the relevant checkout on an online machine. Committed cloud reads identify a recorded ref; they do not include unflushed local edits. Use **Open workspace** when you need machine work, and start a machine explicitly if none is online.

An open portable workspace has its own Git repository. Inspector can browse its local files and staged or working changes without the project's base checkout. ArtifactFS is a machine-side checkout option, not the authority for conversations or evidence. Its host and repository requirements are separate from cloud repository access.

Base comparisons use the original branch commit from the base space's latest published checkpoint. Inspector fetches any missing Git objects into the inspected workspace and compares changes from the merge base. It does not reopen the base space or include the base space's saved uncommitted changes. If the checkpoint is unavailable, the base comparison reports that error; files and local changes remain available.
