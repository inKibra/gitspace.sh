# Agent workflow

GitSpace treats agent work as a lifecycle, not a chat window.

## Plan

Start with the **Goal**. Record the outcome, constraints, and observable requirements before implementation changes the shape of the problem.

Use the **Workflow** when the workspace needs an explicit execution contract. Use the **Rubric** to make review criteria concrete before judging the result.

An agent's default plan file is `local://workspace/PLAN.md`, or `local://base/PLAN.md` for a project agent. New root sessions keep that artifact scope. Subagents do not inherit the parent's selected plan. No plan file is required to start work.

## Build with context

The workspace agent runs in a cloud-owned Pi Session. Conversation history, questions, and task records survive a machine disconnect. Provider requests and credential refresh run in the cloud; they do not require an online machine. Repository file reads, edits, and ordinary searches use the cloud-owned working copy. Shell commands, structural search, and lifecycle execution require an attached machine cache.

Structured agent questions appear as native interactions. Answer the decision directly without searching terminal output for a prompt.

Under **Inference → your profile → Agents**, **Default approval mode** chooses how new conversations start: **Auto-approve** (the default), **Ask for writes**, or **Always ask**. Each conversation adopts its default once; later profile edits do not overwrite that conversation's mode. Change an existing conversation from its composer menu.

Machine-backed tools check for an available executor before asking for approval. A completed attempt can still return its saved receipt after that machine disconnects; this does not rerun its command. Approval modes never grant new signed-in Chrome access: project browser approval and allowed-domain restrictions still apply.

The live workspace view shows a bounded window of recent messages and completed tasks. Older history and task receipts remain in durable storage. Reconnecting can replace the live view with a fresh snapshot; it does not replay an uncertain machine effect.

For repository setup, use the built-in `workspace-lifecycle` skill. It inspects the repository and CI, proposes the lifecycle split, and asks permission before editing. Execution needs separate human approval of the final content. Agents use the `environment` tool for authorized runs and logs; they cannot grant content approval, recover uncertain runs, or destroy cloud resources. See [Workspace lifecycle](/workspace-lifecycle).

### Workspace status

The workspace header and sidebar use the same accepted status for the selected workspace. The sidebar keeps a small summary; it does not load each workspace's transcript or agent controls. Leaving a workspace keeps its last-known activity in the sidebar. Newer reads, closing the workspace, and ownership changes replace that summary.

### Context compaction

The session's compact action asks Pi to summarize a conversation prefix. It uses the conversation's admitted inference profile and model. The summary instructions ask it to preserve goals, constraints, decisions, unresolved questions, file paths, and tool results needed to continue. An empty, failed, or aborted summary is an error.

Compaction runs in the cloud and follows Pi's task lifecycle. It does not require the conversation's machine checkout to be online.

### Delegate read-only work

Use `agents` with `op: 'spawn'`, a complete `task`, and exactly one selector: `agent` for a granted agent-file name or path, or `role` for a configured model role. Optional `name` sets the child's address, not its model or definition. Set `background: true` when the child must outlive the foreground turn.

```json
{ "op": "spawn", "role": "review", "name": "Reviewer", "task": "Review the changed API for compatibility." }
```

The selected file or role supplies the child's own settings. A child inherits repository instructions and rules, not the parent's plan, skills, or execution settings. GitSpace records the exact definition content and revision, selection, role, admitted model, and address at spawn. Editing the source file does not change an existing child. Its definition view is read-only.

Session controls for a child conversation support inspection only. Send workspace changes, browser controls, and other mutating session commands to the workspace's root conversation.

Children can use `read`, `find`, `grep`, `ast_grep`, `history_search`, `history_read`, `web_search`, `todo`, the headless browser, and agent messaging. They cannot access the user's relay browser. A definition can narrow this allowlist, but cannot grant writes or nested spawning. Children can message their parent and siblings; they cannot spawn or stop agents.

Use `agents` with `{ "op": "send", "to": "Reviewer", "message": "Focus on removed fields." }`. Addresses can be names or conversation IDs; children can use `parent`. `list` and `status` show the conversation family. Messages enter durable history with the sender's name and ID.

`{ "op": "wait", "timeoutMs": 30000 }` returns the first pending event, a timeout, or a stopped result. It does not wait for every child. Messages, command completions, and process exits can each wake a wait.

**Stop** stops the selected conversation and its descendant tree, including owned background commands and supervised processes. It does not stop unrelated workspace processes. Events that arrive while stopped remain queued. Only an explicit user message resumes delivery.

### Run commands and processes

Use `bash` for finite commands. `cwd` defaults to the repository root. A background command returns a durable `job` handle immediately and delivers its completion automatically.

```json
{ "command": "bun run build", "background": true }
```

Use the same `bash` tool with `op: 'list'` to discover this conversation's background commands. Pass the returned `job` object unchanged to `status`, `wait`, `logs`, or `cancel`. `wait` accepts `timeoutMs`; `logs` accepts `lines`, `head`, and `cursor`. There is no separate `jobs` tool.

Use `proc` for services and interactive programs. A start request takes a typed `spec` with `name` and `application`; put arguments in `spec.args`, not in a shell command string.

```json
{
  "op": "start",
  "spec": {
    "name": "web",
    "application": "bun",
    "args": ["run", "dev"],
    "ready": { "port": 5173, "timeoutMs": 30000 }
  }
}
```

The spec defaults to the repository root for `cwd`, `pty: true`, empty `args` and `env`, `restart: 'no'`, `persist: true`, and `detached: false`. Readiness can check `log`, `port`, and optional `host`. A readiness timeout leaves the process alive; inspect `timedOut` and `matched` before claiming it is ready.

Address later `proc` operations by `name`. Use `list`, `status`, and `describe` to inspect processes; `wait` accepts `for: 'ready'` or `'exit'`, an optional `pattern`, and `timeoutMs`. `logs` supports `lines`, `head`, `grep`, `cursor`, `follow`, and `timeoutMs`.

Send terminal input with `op: 'send'`, `text`, and optional `enter` (default `true`) or `keys`. The same operation accepts `signal`, or `cols` and `rows` for resizing. Use `stop` or `restart` to change process state. Exits of agent-started processes produce durable notifications.

Process visibility spans the workspace, not just the current conversation. Private processes and processes outside that workspace stay inaccessible. Read-only controls (`list`, `status`, `describe`, `logs`, and `wait`) do not require approval. Mutating operations follow the session's normal plan and approval rules.

Exit tracking and conversation Stop keep the original process identity. They use that machine's current ready attachment and remain pending while it is unreachable.

## Configure account and project access

**Skills**, **Plugins**, **Secrets**, and **Crons** are account pages. You can manage them with no workspace open and no machine online. Selecting a project does not change an account-level write into a project-level write.

**Inference** loads provider and model catalogs for the selected profile. Until the model catalog is ready, saved model choices stay visible but cannot be changed in the model picker. A loading catalog does not mean that a model or provider is missing.

Skills have account defaults and per-project assignments. Set their use in the project's main space separately from their use in its workspaces. Root agent sessions refresh those assignments before their next prompt or provider request. A settings change does not wake an idle agent or erase instructions already in its conversation. Subagents do not copy the parent's skill assignments.

Plugins keep connections in the account library. Grant each connection to the projects that need it, with separate project-space and workspace access. Connecting or enabling a plugin does not grant every project access. Tool calls check current grants, connection settings, and secret access, including calls through a cached tool handle. If those checks cannot reach the account, the call fails rather than using stale permission.

Account secrets are shared only through explicit project grants. Each grant chooses project-space access, workspace access, or both. A project secret with the same name overrides the granted account secret. Revoking the account grant removes inherited access but leaves the project's own secret intact. Management pages return secret metadata, not stored plaintext.

Use account values for non-secret defaults and project values for overrides. Lifecycle values resolve from bundle default to account, project, then workspace value. See [Lifecycle reference](/lifecycle-reference) for profile requirements and secret resolution.

Crons list schedules across the account. Choose the owning project when creating one. You can manage schedules and read their history without opening that project; execution still needs an eligible online runner.

A cron submits its prompt to the existing root conversation, not a new conversation for each run. Scheduled prompts run one at a time. The schedule's read and write scopes constrain its own turns and work spawned from them, not unrelated user turns.

Queue time does not count toward the one-hour runtime warning. A run that waits longer than one schedule interval or 24 hours, whichever is shorter, is withdrawn and recorded as **Skipped: workspace busy**. The next due run starts fresh.

After an hour of execution, GitSpace marks the run **overdue** and posts a notice without stopping the workspace agent. History records the real result when the turn ends.

In **Run history**, **Cancel queued run** withdraws only that submission. For a running cron, **Stop workspace agent** requires confirmation because it also interrupts child agents and other workspace work.

## Manage workspaces from an agent

Agents use typed tools directly, not a CLI or a JavaScript `space` namespace. `space_workspace` with `args: { method: 'list' }` discovers workspace definitions in the current project, including closed workspaces. Method `current` reads the current workspace.

Use `space_workspace` with `args: { method: 'create', name, branch, sourceKind, sourceRef }` to create a workspace. Optional fields include `phase`, `dependsOn`, `goal`, `workflow`, and `rubric`. Check the returned `ready` field. If an instruction write fails after creation, the result includes the created workspace identity and completed writes so the agent can repair that workspace instead of creating a duplicate.

New workspaces start in Plan when `phase` is omitted. The browser creation dialog also defaults to Plan; selecting another phase explicitly (including creation from a board column) keeps that choice, subject to dependency phase ceilings. Existing and restored workspace phases are unchanged. Initial Goal and Workflow drafts remain separate typed instructions and are not rewritten by the workspace phase default.

For a remote branch, use `sourceKind: 'branch'` with a reference such as `origin/develop` or `refs/remotes/origin/develop`. GitSpace fetches that source with the project's repository credentials; it does not require a cached tracking reference or an open base checkout.

For another workspace, use `sourceKind: 'workspace'` and its workspace ID as `sourceRef`. A locally held, open source contributes its actual committed HEAD. A closed or remotely held source contributes its latest published checkpoint's committed HEAD, even when its checkout is absent. Creation does not open or transfer the source, change its branch, or include uncommitted changes. The source remains the new workspace's dependency and stacked-on parent, with dependency phase ceilings enforced from the canonical catalog.

Source resolution and destination branch validation happen before publishing the new workspace. An invalid source or branch does not leave a new failed workspace entry.

`space_phase` changes the current workspace's phase. The `space_workspace` tool also supports `setRelations`, `open`, and `restore` under the workspace lifecycle and checkpoint rules. Keep the revision and placement generation from the latest read; stale changes reject. An agent cannot close or archive its own workspace from a running tool. Use the browser for that action.

Pass `workspaceId` inside `args` to `space_goal`, `space_workflow`, or `space_rubric` to edit another workspace in the same project. Use method `get` to read, `describe` with `operation: 'put'` for the input schema, and `put` to write. Closed workspaces stay closed. Writes require the record's `expectedRevision`; use zero only when creating an absent record.

Instruction changes post a notice to the affected agent session without interrupting its current tool or starting an idle turn. The agent reads the latest Goal, Workflow, and Rubric before its next provider request.

## Preserve decisions

The **Journal** records phase narrative, decisions, artifacts, and state changes. It explains how the workspace reached its current state without asking a reviewer to reconstruct the story from a transcript.

Use the journal for durable reasoning. Keep temporary narration in the agent session.

## Verify with evidence

A completion claim is not proof. Attach evidence that demonstrates each observable requirement:

- A browser run for a web behavior.
- Runtime output for a service or CLI behavior.
- A focused test for a permanent contract that cannot be exercised directly.
- An artifact when the output itself is the deliverable.

The **Review** product keeps discussions attached to files, hunks, lines, or the whole workspace. Resolve the concern, not just the thread state.

## Keep and share artifacts

Agents read and write artifacts with ordinary tools through `local://workspace/<path>` and `local://base/<path>`. Workspace agents can read project artifacts but write only their workspace artifacts. Project agents can write project artifacts. Published edits refresh the browser catalog and open artifact views; evidence references still point to their recorded version.

These encrypted `local://` evidence files are separate from Cloudflare Artifacts repositories, which store code. A published code view names a committed snapshot; it does not include unflushed changes in a machine checkout.

In **Artifacts**, select one or more workspace files and choose **Copy to project artifacts**. Each copy is an independent project file with source provenance. The originals remain. Choose another destination when a file already exists, or explicitly confirm replacement of its displayed version. A newer destination version invalidates that confirmation.

Select one project or workspace artifact and choose **Share** to create a link to that fixed version. Set an optional expiry, copy the link, or revoke it from **Active links**. Later edits do not change the download.

Anyone with the link can download the artifact without signing in. Do not share secrets. GitSpace serves public artifacts as attachments and does not put encryption keys in the URL. Revoking a link stops new downloads, but cannot remove copies someone already downloaded.

## Explain the change

The **Change Guide** turns the current diff, goal, journal, and evidence into a review path. It should explain the behavior, important code paths, tradeoffs, and proof. It is not a generated file list.

## Operate the result

Shipping code does not make the workspace irrelevant. Keep services, events, release state, unresolved review threads, and rollback information with the workspace until the work is quiet.

Move the workspace through `plan`, `code`, `review`, and `ship`. Archive or release it only after the operational state agrees with the completion claim.

## Direct attention across the fleet

The fleet view distinguishes work that is active, waiting, failed, or needs attention. Machine placement identifies the checkout and effect executor, not the owner of the conversation. Restarting an agent does not restart its machine processes, and losing a connection does not prove those processes stopped.
